# 豆包工作独立端审稿

## 适用范围

只有稿件专项、标题或核心承诺明确属于“`双端选题-独立端`”“`独立端`”“`小端`”，或明确在官宣独立客户端“豆包工作”时，才应用本规则。普通课程教学稿里出现“豆包工作”四个字，不足以切换路由。

“豆包工作”是与普通豆包不同的独立客户端，是正式发布、面向生产力和办公场景的 AI Agent。达人可以用自己的话表达，但不能把它写成一个话题、单项功能或普通豆包里的模式。

## 两项硬要求

1. **开头完成官宣和定位。** 开头要让第一次听说的人马上知道：正式发布了什么产品，它解决哪类生产力或办公问题。允许先用一句短钩子，但不能讲了半篇后才解释“豆包工作”是什么。
2. **飞书关系必须出现。** 讲清豆包工作与飞书的原生关系即可，例如账号打通、成果留在飞书生态继续协作、继承飞书权限体系。按稿件主线选择最有用的两三点，点到为止，不要求抄完 toB 清单。

缺少上述任一项，属于 `hard_rule`。评论应说明观众会误解什么，并给出最低成本补法，不把内部模板原文贴给达人。

## toC 是核心发挥区，不是功能点名册

多端与云电脑、浏览器操作、创作模型、应用生成、办公能力等，只是供达人开拓的方向。可以选一项讲深，也可以组合几项或开拓清单外的方向。不得因为没有覆盖其中某一项而批注；只有稿件自己选择讲了某项能力却讲错、讲空或破坏主线时才提出修改。

内容质量优先于覆盖数量。大纲是参考结构，不是逐字稿或固定段落顺序；达人可以按自身风格调整开头、toB、toC 和结尾，只要两项硬要求成立、主线完整、事实准确。

## Skill 与案例的教学关系

稿件选中的主讲 Skill 继续使用课程教学标准：

- 先用普通用户能理解的语言讲清 Skill 是什么、适合哪些场景、能做什么、主要产出什么；
- 再借用例讲使用思路：准备什么资料、提示词为什么这样写、关键选择和优化方法是什么、换一个对象如何复用或进阶；
- 最后结合产物说明好处落在哪里，例如省时间、降门槛或提高稳定性；
- 用例负责帮助理解和证明效果，不能让整段只剩“这次案例怎么做”。

不要求机械三段式。判断的是观众看完后能否举一反三，而不是文稿有没有出现固定术语。

## 双端互通与云电脑

这是两个独立能力：

- **双端互通：** 电脑本地已经在跑的任务，可以在手机上实时同步查看并继续发提示词或修改指令；本地电脑需要保持开机。
- **云电脑：** 任务从一开始就在云电脑中启动，适合大量调研、资料处理和长时间任务；不占用本地电脑资源，本地电脑关机也能继续。
- 本地电脑已经开始的任务不能中途切换成云电脑任务。

浏览器 Skill 接到一次指令后自主搜索、检测、筛选和整理，也可以叫自动检测或自动执行；“自动”不等于“定时”，更不等于“云电脑”。

只有稿件实际讲了这些能力才核对事实。专用模板列出它们，不代表每篇都必须全部出现。

## 当前活动权益

“30 天送会员权益”只按当前生效的活动口径和审稿记忆碎片审核。活动时间、资格或说法变化后，不能继续靠历史模板硬性要求；落评论前必须核对当前口径。

## 审核尺度

- 开头未官宣产品或定位错误：`hard_rule`。
- 完全未提飞书原生关系：`hard_rule`。
- 把双端互通写成云电脑、声称本地任务可中途切云端：`feature_error`。
- 主讲 Skill 仍被案例淹没、观众无法复用：按课程教学标准判 `editorial_required`。
- 只是不喜欢达人的结构、没有覆盖某个可选能力、或还能补更多案例：`optional_improvement`，不落达人可见批注。
