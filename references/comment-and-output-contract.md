# 批注与交付契约

## 批注层级

先判断是否真的值得打扰达人。以下四类才写批注：

1. 当前明确口径冲突，例如平台命名、生效 Shard 明确要求的双端前置、禁用旧称。
2. 功能描述与实际操作/画面明显不符，可能直接误导观众。
3. 专项方向、脚本主线或关键操作缺失，导致稿件无法按当前 Brief 推进。
4. 内容本身存在会直接阻碍观众理解、跟做或成片节奏的问题，例如教程核心能力只讲当前案例却没有先建立通用认知、没有说清主要产物、开头承诺与正文不对应、两段重复同一作用、结尾反复收束或铺垫过长并挤掉关键讲解。这类必须能引用当前原文并给出具体改法。

普通营销表达、可从演示直接看见的效果、个人体验和轻微措辞偏好不批注。内部判断中的“证据不足、无法核验、绝对化、边界不清”等术语，不得直接写给达人。

静态文档未附完整录屏，不等于达人没有拍或功能没有展示。只有正文、分镜、画面说明之间存在明确冲突，或者会议/Brief 明确要求的核心步骤完全缺失，才要求补拍；不能因为审核模型“看不到结果页”就要求达人自证。

写批注前必须完成一次内部反事实检查：如果不修改，观众是否会被明确误导、无法跟做，或成片是否会因明显重复、过长、位置失当而削弱教程主线？如果只是“还能讲得更好”“可以多展示一个功能”“换一种 Skill 更优”，不写达人评论。

每个问题还必须带三个内部字段：

- `basis`：只能是 `hard_rule`、`text_contradiction`、`feature_error`、`high_risk`、`editorial_required`、`optional_improvement`。
- `evidence`：原稿中可逐字找到的 1–4 段证据；文本矛盾至少两段。
- `ruleRef`：仅 `hard_rule` 必填，写清当前 Shard、会议确认项、Brief 或平台规则。

系统默认拒绝 `optional_improvement`。`editorial_required` 必须同时有原稿证据、具体理解障碍和可执行改法。局部问题若选区不在原稿中、文本矛盾凑不齐两处原文、功能错误没有锚点、硬规则没有来源，一律不落评论。

以下内容不得落达人评论：

- 把手机远控电脑误判成云电脑，或要求把主动远控改成被动“查看进度/结果”。
- 把浏览器 Skill 接到一次指令后自主完成检测、筛选和整理，误判为“没有定时任务所以不算自动”；自动执行、定时触发和云端运行是三个不同维度。
- 原文已经明确手机操控电脑、继续任务或双端同步，却只因没有拆成固定步骤再次要求补双端演示。
- 静态稿未附未来录屏、画面或截图，但正文并无事实矛盾。
- 待确认名单显示姓名、暂缺学号等正常业务信息。
- 先上传素材、再选择表格整理，或先创建 Skill、再输入素材运行等能够成立的操作顺序。除非脚本前后明确互相否定，不能因为审核者偏好另一种顺序而批注。
- 仅凭静态文稿推测未来画面、录屏、截图会对不上；审稿对象里没有该画面，就不评论画面。
- Skill 的可选扩展、组合优化或表达偏好。

### 局部批注

用于错误词、平台禁用表达、逻辑跳步、功能描述不准等可以锚定到原句的问题。

- 选中最短但完整的词句。
- 评论正文控制在 1–2 句，优先不超过 80 个汉字。
- 直接说这句话哪里容易误解，并给可直接替换的写法；不要写审查腔。
- 内容方向成立但需要压缩、合并或换位置时，可以先简短确认，例如“内容没问题，但这里和上面重复了”，随后直接给修改动作。
- 不写“证据链、边界不清、能力闭环、缺乏验证、请自证”等内部术语。能一句说清就不要写两句。
- 示例：`这里还是旧称。改成“豆包工作”，后文同类表述一起统一。`
- 示例：`这里别写成“同步整台电脑”，容易让人误解。改成“把素材放进指定文件夹，AI 读取后把结果存回对应文件夹”。`

### 整体意见

用于主线、结构、达人适配、系列递进或整体操作证据不足。

- 不创建文末全文评论，也不额外发送只有“审核结论/详见批注”的汇总评论。
- 整体意见直接锚定在正文前部的“大纲”“脚本”“内容综述”等标题上；优先选择“脚本”，其次“大纲”或与问题最接近的前部标题，保证达人打开文档就能看见。
- 文档没有可用标题锚点时停止写入并进入待处理队列，不得退化为文末全文评论。
- 先写最影响成片的一项，再写修改顺序。
- 同类问题合并，不把全文拆成几十条碎评论。
- 课程教学若整体被用例吞掉，应优先在“大纲”或“脚本”标题上写一条整体意见，说明“教程主体应回到 Skill 的功能、使用思路和好处”，再用少量局部批注指出最适合补方法的位置；不要围着案例里的每个数字和结果逐条挑。
- 表格评论只能锚在单元格时，涉及整个 Skill 教学过程的意见必须在评论里写明“这一整个 Skill 段落”，并说明内容可分布到引入、操作和结果部分；不能写得像只改当前这一镜。
- 语气面向达人和机构，说人话，不使用“信息架构、叙事闭环、证据链”等内部术语。

## 结论

- `可推进`：没有必须修改的问题。轻微表达优化不写评论。
- `修改后复审`：存在影响任务真实性、结构、平台口径或操作完整性的明确问题。
- `待确认`：规则冲突、来源不足或脚本并非完整稿，不能硬判。

只允许 `blocking` 或 `major` 问题进入飞书评论。`minor` 不落评论、不触发复审。

## 内部卡片

仅列本周期实际完成审核的脚本：

- 标题：`脚本审稿完成｜N 篇`
- 摘要：通过、修改后复审、待确认数量。
- 明细：一行一个原文档标题超链接，后跟结论；不展示来源 ID、Token、模型推理或内部规则。
- 没有新脚本时不发空卡片。

## 幂等

- 审核键：`规则版本 + doc_token + revision_id + 内容哈希`。规则升级后允许按新口径重审。
- 问题键：`审核键 + 锚点 + issue_code`。
- revision 不变不重复审；revision 变化才复审。
- BOT 已评论过的问题不重复写；写失败保留草稿与错误，等待重试。
