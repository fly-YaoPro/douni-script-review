# 内容审稿框架

## 第一步：还原这篇稿子

在下结论前先生成内容地图：

- 目标受众：谁会看、他现在卡在哪。
- 核心承诺：看完能理解、学会或得到什么。
- 内容类型：教程、体验、案例、剧情、口播、测评或混合形式。
- 能力清单：稿件实际说到或演示了哪些产品能力、Skill 和操作。
- 段落作用：开头、痛点、能力解释、操作、结果、扩展、转场、结尾。
- 教学单元：把能力分成 `primary`、`supporting`、`mentioned`。
  - `primary`：本篇主要教的能力。标题、封面、开头或核心承诺并列承诺多个 Skill 时，每个都属于 `primary`，必须分别检查用户问题、能力解释、关键动作、可观察结果、用户价值和教程深度。
  - `supporting`：用于支撑主线的能力，只需完成当前作用，不强制扩写成完整教程。
  - `mentioned`：顺带提到的能力，不因没有展开而判错。

不先完成内容地图，不能直接开始挑错。

内容地图中的“段落作用”不是标签装饰。主编必须为每个主要段落判断：它本来要完成什么、现在是否完成、是否与相邻段重复、是否放错位置。比如一段本应介绍 Skill，却只继续铺案例痛点；一段已经适合结尾，后面又用相同观点重新收束；这些都属于段落职责没有处理好。

## 第二步：产品核验

针对内容地图里的每个真实能力点读取对应知识，不按关键词猜：

- 功能叫什么、解决什么问题。
- 用户实际输入或操作是什么。
- 运行环境和前提是什么。
- 输出/结果是什么。
- 原稿是否把相邻但不同的能力混在一起。

只评论稿件实际声称的内容；文档未展示未来画面，不等于能力未实现。

## 第三步：内容编辑

先做一次“善意理解”：假设作者已经尽量利用口播、画面、表格和分镜表达，找出这篇内容最可能成立的版本。然后再问三个问题：

- 它承诺教会什么，而不只是出现了什么能力名？
- 观众看完后掌握的是按钮路径、一次结果，还是能迁移到下一次使用的判断？
- 如果有多个并列主讲能力，正文投入和教学深度是否与承诺大致匹配？不要求平均篇幅，但不能一个讲透、另一个只用结果凑数。

逐段判断：

1. 开头是否让目标用户快速知道内容与自己有关；剧情、体验型开头按其自身逻辑判断，不强制套教程模板。
2. 痛点是否真实且与后面的解决方案对应。
3. 每个 `primary` 教学单元是否先让观众建立通用认知：这是什么、适合什么任务、能完成什么、主要会产出什么，再让当前案例承担操作和证明效果。痛点或结果钩子可以在前，讲解也可以穿插，但不能先把案例过程讲完，观众仍不知道这个 Skill 换个对象还能怎么用。允许图片、表格、分镜和紧邻的操作说明共同承担信息，不要求口播逐句复述。
4. 单独判断教程深度：区分“提到、演示、教会”。按钮路径、输入输出和最终成片通常只能证明演示过；真正教会至少应让观众理解一个对当前任务有决定作用的判断，例如素材如何取舍、参数为什么这样选、提示词怎样组织、结果哪里不对以及如何调整。这里不是固定五选一清单，模型要结合当前 Skill 找到真正影响复现的那一步。
5. 对课程教学稿，再判断案例和教程的主次：
   - **功能**：观众是否理解 Skill 的通用应用场景、能实现的效果和主要产物，而不只是本次案例做了什么。
   - **使用思路**：观众是否知道如何顺着 Skill 的能力准备输入、组织提示词、选择或优化产物，并能把方法迁移到另一个同类任务；进阶用法按篇幅取舍。
   - **好处**：稿件是否借真实产物解释省时、降门槛或稳定性中的至少一个真实价值，而不是只说“方便、高效”。
   这三个维度可以散落在全篇，不能机械按字段打勾。核心判断是：删掉案例中的公司名、产品名或具体数字后，观众还剩下多少可复用的方法；若几乎只剩操作流水账和结果罗列，教程主体就被用例吞掉了。
6. 操作是否有必要的前提和关键步骤；画面可直接承担的信息无需口播重复。
7. 结果是否回应开头承诺，是否属于该产品或作者实际完成的事。
8. 相邻段落是否重复同一信息、关键转折是否突然、结尾是否完成本篇任务。判断重复时看“作用”而不只看字面：两段换了说法却都在做同一次总结，也算重复；一段内容本身成立但放在当前位置拖慢节奏，可以建议压缩、前移、后移或删除重复部分。
9. 表达是否像真实用户在分享自己的使用过程，而不是堆产品说明。

不要套固定模板。教程、体验、剧情、案例、口播的结构可以完全不同；真正要判断的是当前内容是否把自己的主线讲成立。某个能力只承担转场或举例时，不得因为没有完整教学步骤就要求扩写。

发现核心问题时，先给出“这篇稿子为什么没有把自己的承诺讲成立”，再选择最低成本的修法。修改动作不限于“补充”，也可以是压缩、合并、换位置或删除重复内容。不要一次罗列所有可能补充项；若补一个关键判断、合并两段或前移一次功能解释就能成立，只要求这一处。

## 问题分级

### 必须修改

- `hard_rule`：明确生效口径或规则冲突。
- `feature_error`：产品事实、操作、输入输出或运行环境说错。
- `text_contradiction`：稿件自身两处原文互相冲突。
- `high_risk`：确有风险且原文能举证。
- `editorial_required`：虽非产品错误，但会让观众误解主线、无法理解/跟做、教程核心没有讲清，或因明显重复、过长、位置失当而实质影响成片节奏和教程主次。

当标题或核心承诺把多个 Skill 并列作为教程卖点时，任一主讲 Skill 只有表层流程、没有真实操作判断，即属于“教程核心没有讲清”，不是可选优化。

### 不打扰达人

- `optional_improvement`：只是更顺、更有趣、功能更多或 Skill 组合更优。
- 个人措辞偏好、未见未来画面、未按审核者喜欢的顺序演示。

`editorial_required` 必须同时满足：能引用当前稿件原文、能指出具体理解或成片障碍、能给出可执行修改。缺一项就降为可优化。评论可以先用一句人话确认成立部分，例如“内容没问题，但这段和上面重复了”，再直接说压缩、合并或移动到哪里；不要为了显得客观写成长篇审查说明。
