# 真人审稿案例库

案例库用于补足审稿中的隐性判断，不是另一套业务规则。

## 当前规模

- 23 份抖音脚本案例。
- 127 条真人评论卡片。
- 构建程序会把评论区分为：内容编辑、产品口径、动态活动、拍摄执行。
- 运行时只允许使用质量合格的“内容编辑”案例；其余案例仅保留作审计与后续人工整理。

原始来源登记在 `human-review-case-sources.json`，结构化产物在 `human-review-case-library.json`。新增或更新来源后运行：

```bash
npm run script-review:sync-cases
```

## 运行时选择

1. 先完成当前稿件内容地图，不能由案例替当前稿件补内容。
2. 排除当前正在审核的同一文档，避免拿它自己的历史批注推导答案。
3. 按平台、专项、当前教学缺口、问题类型和能力词打分。
4. 每篇最多取 5 条；优先跨文档、跨问题类型，避免某一位审核人的偏好占满上下文。
5. 案例正文和批注作为不可信业务素材进入模型；只有选择规则和优先级契约属于可信上下文。

## 不能从案例继承的内容

- 限免、会员、活动权益等有时效的宣传点。
- “必须前置双端”“必须讲云电脑”等单期 Brief 或临时宣传重点。
- 历史产品名称、入口路径和具体操作事实。
- 某个审核人指定的达人方向、Skill 组合、拍摄形式或素材安排。
- 评论的解决状态。`is_solved=true` 只说明评论卡片被关闭，不自动等于意见正确或已采纳。

以上内容如需判断，必须回到当前碎片、最新会议、当前 Brief 和产品能力资料。

## 审计

每次审稿在 `script_review_items.result_json.reviewCases` 中记录实际选中的案例 ID、来源文档、问题类型和链接。工作台可以据此回答“这条意见参考了哪些真人案例”，但给达人发送的评论不得暴露内部案例库。
