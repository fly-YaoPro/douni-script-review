# 2026-08-24 审稿要求对齐｜逐字稿口径

本页来自完整妙记逐字稿，不是智能纪要。审稿时按这里理解会议结论，不把讨论过程中的未确认提议当成硬规则。

## 共通判断

- 先看选题是不是达人真实会遇到的工作或学习问题，做法是否确实能提高效率。
- 再看是不是 Agent 用法：可以是 Skills 组合、vibe coding 或连续工作流，不限定成某一种固定产物。
- 不为所有选题统一编造数量门槛。不同 Skill、达人和场景的合理操作轮次不同。
- 完整脚本才进入豆尼审核；大纲由人工继续细化。
- 文案面向普通用户，说人话，不写成论文或产品说明书。

## 工作任务

- 更像普通用户分享真实用法：痛点和任务是主角，Skill 服务于任务。
- 可以自建 Skill、克隆开源 Skill 或组合内置 Skill。
- 自建 Skill 的合理过程是：先给一个想法或核心输入，让 AI 出初版，再结合达人经验调整并复测。不能反过来要求所有信息都必须人工预先填全。
- 克隆 Skill 后应体现个性化修改与结果验证；内置 Skills 应围绕同一个任务自然协作。
- 开头尽快交代问题和结果，再进入操作。是否需要补步骤取决于观众能不能看懂，不机械数交互次数。

## 课程教学

- 更强调功能教学：Skill 是主角，场景用于帮助理解。
- 可做 0 到 1 的系列教程，也可讲双端互通、云电脑等组合能力。
- 一期可讲 2–3 个 Skill，也可以跨行业举例；只要主次清楚、观众能跟做，就不按工作任务的“单一场景”规则拦截。
- 会议当期确认双端互通需要出现；后续是否继续强制及放在什么位置，由当前审稿 Shard 和 Brief 控制。手机远控实体电脑后，可以继续输入 Prompt、推进电脑端任务和查看结果；这属于真实的双端互通，不等于手机本地运行 PC Skill，也不等于云电脑。
- 双端表达不能退化成一句口号。当前 Shard 若要求重点透传，应通过使用场景、手机端的具体操作和电脑端持续执行的结果，让普通用户真正理解其方便与独特性；但不机械要求固定步骤或统一句式。
- 云电脑可并列或组合，但它是独立能力，重点是重任务在云端继续跑、减少本机占用等。不能因为脚本写了手机远控，就强制要求补云电脑，也不能把手机远控降级成只能“看进度”。
- 三万粉以下的 KOC 优先走双端/云电脑方向。
- 30 天免费活动按当期客户口径决定是否必须提，不能拿旧时间节点机械套用后续稿件。

## 平台与名称

- 抖音可以口播和画面出现“豆包”。
- 小红书继续用“AI”表达，产品名和 Logo 按当前平台口径处理。
- 会上对统一新名称仍有讨论；会后已确认：只有指代专业版、工作任务模式的内容统一称“豆包工作”。普通产品名“豆包”仍可正常说，不得机械替换。

## 审稿尺度

- 会议没有要求全面收紧营销表达，也没有要求所有效果都提供第三方证明。
- 画面、操作过程和达人亲身结果本身就是可用依据。
- 静态稿件没有附完整成片，不代表相关画面不存在；除非脚本与分镜明确冲突，不能以“没有看到结果页”为由批注。
- 只有功能说反、平台口径错、核心步骤缺失、专项逻辑不成立或真正高风险承诺，才要求修改。
- 会议讨论中出现的优化想法不自动变成硬规则。更好的 Skill 组合、扩展方向和演示细节只做内部建议，除非原方案本身无法完成。
