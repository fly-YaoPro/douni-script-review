# PC 场景与 Skill 能力审核

本页解决两个容易误判的问题：一是把“可以优化”误写成达人必须修改；二是没有理解真实电脑、手机远控、云电脑和 Skill 的实际边界。

## 先做四层判断

每个疑点都先在内部完成以下判断，不能看到一个关键词就评论：

1. **还原作者在说什么**：结合前后文、操作说明、表格、分镜和结果描述，选择最符合普通人理解的含义，不主动往错误方向脑补。
2. **核对真实能力与专项硬口径**：只核对会影响事实、平台、专项方向或能否执行的部分。
3. **给疑点分级**：
   - `硬错误`：功能说反、操作无法完成、当前硬口径冲突、主线跑偏。
   - `待确认`：原文真的无法判断，而且不同答案会改变能否发布。
   - `可优化`：有更好的写法、Skill 组合或扩展方向，但原方案本身成立。
   - `成立`：按真实产品和普通语义可以完成。
4. **反事实检查**：如果不改这句话，观众会不会被明确误导，或达人会不会无法按稿执行？答案是否定的，就不要给达人留评论。

只有 `硬错误` 且能给出直接证据时才默认落批注。`待确认` 进入内部确认；`可优化` 仅保留在内部审稿记录，不能包装成“必须修改”。

## 批注证据门槛

每个问题必须归入以下一种依据：

- `hard_rule`：与当前生效 Shard、最新会议确认项、当期 Brief 或平台硬规则直接冲突，必须写清具体规则来源。
- `text_contradiction`：同一脚本中至少两处可逐字定位的内容互相矛盾，例如同一结果分别写成 18 条和 23 条。
- `feature_error`：原句把真实功能说反、写成不存在的能力，或给出无法执行的操作。必须锚定原句。
- `high_risk`：明确承诺收益、录取、疗效，或暴露密码、证件号等真实敏感信息。
- `optional_improvement`：还能更顺、更好看、更完整，或模型只是没看到未来画面。不得落达人批注。

模型说“没有看到、建议补充、证据不足、可以优化”本身不是问题证据。局部批注引用的原句必须真的存在；文本矛盾必须同时给出两处原文，不能凭截图想象或审核者记忆判断。

## PC 场景筛选

参考 `doubao-task-mode-cases` 的 PC 场景维度：

- **PC-1**：任务天然发生在电脑工作环境，例如文件夹、桌面软件、浏览器多页面、办公文档或专业工具。
- **PC-2**：有较高的信息密度，通常涉及 15 个以上数据点、资料项、页面元素或多份材料。
- **PC-3**：需要多窗口、多标签、批量输入、长时间处理、跨工具衔接或较重的文件操作。

满足两项及以上，通常适合 PC/Agent 场景。该判断默认只用于内部评估选题是否成立，不要求达人在脚本里逐条证明。只有整条内容明显只是一问一答、轻量手机操作，却硬说成 PC Agent 核心场景时才批注。

## 手机远控、双端互通与云电脑

- 手机远程控制真实电脑，在手机上继续输入 Prompt、下达任务、查看电脑端界面并让电脑继续执行，是成立的双端互通用法。
- 这不是云电脑，也不要求补充云电脑环境。
- 不要把主动远控改写成“手机只能查看进度或结果”。手机可以继续操控电脑和推进任务。
- 云电脑是另一条运行环境：任务必须从一开始就选择云电脑，适合大量分析调研、资料处理和长时间任务；任务跑在云端，不占用本地电脑资源，本地电脑关机也能继续。本地电脑已经开始的任务不能中途切换到云电脑。
- 脚本明确说明手机可以操控电脑端、继续执行或同步修改，即已体现双端能力；不机械要求把连接、下指令、执行、查看结果拆成固定四步，也不因没有出现“云电脑”而判错。
- 当前 Shard 若要求“双端不能一句带过”，就看稿件是否给了真实场景、具体操作和实际方便点，而不是机械数句子。至少应让观众明白“什么情况下用手机、手机具体让电脑继续做了什么、为什么这比守在电脑前方便”；信息已经讲清就不因措辞或段落位置继续挑刺。

## 自动执行、定时触发与运行环境

这三个维度必须分开判断，不能看到“自动”就默认等于“定时任务”：

- **自动执行**：用户发出一次指令后，Skill 自主连续完成多步操作。例如浏览器 Skill 自动打开页面、搜索、检测、筛选并整理结果。即使没有设置定时任务，也可以称为“自动检测”“自动监测”或“自动抓取”。
- **定时触发**：任务在预设时间或周期到来时自动开始。只有原稿明确承诺“每天几点自动启动”“每小时无人操作也会运行”等能力时，才核对是否配置定时任务。
- **运行环境**：任务究竟跑在本地电脑还是云电脑，与是否自动、是否定时无关。自动执行既可以发生在本地，也可以发生在云端；定时任务也不等于云电脑。

审核时先问原稿实际承诺的是哪一层：它是在说“执行过程中不用人逐步操作”，还是“到了时间自己启动”，还是“电脑关机后仍在云端运行”。只有承诺与真实能力不符才批注，不能因为缺少另一个维度就判错。

## 豆包 Workplace Skills 研究方法

豆包 Workplace 当前安装的 106 个内置 Skill 已建立快照索引：`doubao-workplace-skills-catalog.md`。审核涉及 Skill 的脚本时：

1. 识别脚本明确点名或实际描述的 Skill，以及它要解决的真实任务。
2. 核对 Skill 的核心功能、必要输入、主要输出、前置条件和硬边界。
3. 以下情况才批注：把 Skill 能力说反、选择的 Skill 无法完成该任务、关键操作在真实产品中不存在、或把尚未发生的结果说成已完成。
4. 更好的 Skill 组合、可以增加的扩展、提示词优化、演示顺序优化，属于内部建议，不是达人必须修改的问题。
5. 不要求达人在口播里讲完整技术细节，也不要求手工提供所有参数。创建 Skill 时可以先给目标、框架或一个核心输入，让 AI 完成市场分析、初版规划和执行，再由达人调整和复测。
6. 若索引摘要不足以判断硬边界，再以索引中的来源路径读取对应 `SKILL.md` 全文；不能凭 Skill 名称猜能力。
7. 不要要求创作者把 AI 后续会完成的分析工作重新变成人工填参。用户给一个核心输入，由 Skill 自行做市场分析、规划、核算或生成初版，是成立的 Agent 用法；只有对应 Skill 实际不支持该动作时才批注。
8. “创建 Skill”“复制口令后得到同款工具”“输入新素材后重复运行”本身都可以成立。是否需要补一次复测，先看脚本是否已经描述调用和结果；没有成片不等于没有复测。
9. 提到豆包工作或具体 Skill 时，优先检查作者是否用自己的话、从用户视角讲清“它是什么、我怎么用、我怎么理解”。不要求背官方定义；脚本已通过真实任务和操作自然讲明，就视为成立。

## 静态脚本的证据边界

- 当前审核对象是脚本或脚本表格，不是最终成片。不要凭空要求补“画面”“录屏”“截图”来证明一段本来就能成立的文字。
- 只有正文、分镜、操作说明或已有截图彼此明确冲突，才指出“口播与画面/操作对不上”。
- 文档里没有展示某个未来画面，不等于达人不会拍，也不等于流程不存在。
- 待补充名单中只有姓名、暂时没有学号，是正常的业务提醒；不能因此要求隐去姓名或改成编号。只有超出业务必要范围暴露真实敏感信息时才处理。

## 允许的正常表达

“效率翻倍”“省下手动工作”“一键得到结果”“持续执行”“根据输入自动分析”等普通内容表达，只要整体流程能支持其大意，就可以说。不要把审稿变成逐字免责声明检查。只有捏造具体数据、承诺收益/录取/疗效，或把并不存在的能力说成已实现时才拦截。
