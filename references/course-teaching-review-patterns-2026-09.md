## 课程教学的核心任务

课程教学不是展示“这个案例跑成功了”，而是借一个案例把某个 Skill 的通用能力、使用判断和真实价值教给观众。删掉案例里的公司名、产品名、数据和行业名后，观众仍应保留一套下次能复用的方法。

每个主讲 Skill 应在整篇里合起来回答三个问题：

1. **它能干什么**：适合什么任务，会产出什么，与相邻能力有什么差别。用作者自己的话讲，不念官方简介。
2. **我怎样把它用好**：准备什么输入，提示词为什么这样组织，哪个选择影响结果，哪里要检查，结果不对怎样继续改。无需把所有步骤念全，但至少讲清一个真正决定质量的判断。
3. **它为什么值得用**：结合当前产物说明省掉了哪一步、降低了什么专业门槛，或怎样通过固定流程提高一致性与稳定性。只说“方便、高效、几分钟完成”不算讲清。

这三项是跨段落判断，不是强制三段式。功能可以在引入中讲，使用思路可以穿插在操作和修改中，好处可以落在产物对比里。

好处如果单独列成“省时间、降门槛、稳定”口号，通常仍然空。优先在案例产物出现时顺手说明：具体省掉哪一步、少依赖哪类专业判断、为什么下次换素材还能复用。只有脚本结构确实需要总结时，才单列好处段。

多 Skill 教程不套固定的“Skill—案例—Skill—案例”格式。先看真实工作流：若前一个 Skill 的结果会成为后一个 Skill 的输入，应把接力关系讲出来；若只是并列解决不同问题，可以分开短讲。审核的是观众能否理解各自作用和组合原因，不是段落排列是否统一。

## 审稿顺序

### 1. 先还原整篇承诺

先回答：给谁看、这期承诺教会什么、主讲几个 Skill、案例承担什么作用、最后应看到什么产物。没有这一步，不得从某一句直接推导整篇缺项。

### 2. 给每个能力定角色

- `primary`：标题、开头或主体明确承诺要教的 Skill，必须检查功能、使用思路、结果和价值。
- `supporting`：只为主 Skill 提供素材、连接或美化，讲清它在当前流程里的作用即可。
- `mentioned`：顺带提到，不要求展开教程。

并列主讲的 Skill 不要求平分篇幅，但复杂度和承诺应匹配。若三个以上 Skill 都只讲一句功能和一次生成，优先收窄，而不是继续补更多说明。

### 3. 判断是“提到、演示、还是教会”

- 提到：出现 Skill 名或功能名。
- 演示：展示输入、按钮、生成过程或结果。
- 教会：观众知道为什么这样输入或选择、怎样判断结果、换一个同类任务怎样复用。

一条完整 Prompt、三步操作和最终页面通常只能证明演示过。是否教会，要看有没有真实的决策和调整方法。

### 4. 检查案例有没有吞掉教程

以下信号同时出现两项以上，通常是 `case_dominated`：

- 大部分篇幅都在复述当前公司、产品、数据和生成结果。
- Skill 只剩官方简介或一句“选择这个 Skill”。
- Prompt 很长，但没有解释组织方式和关键约束。
- 产物列得很细，却没说这些能力还能用于哪些同类任务。
- 观众只能复制本次口令，换一个对象就不知道怎么改。

修法不是把案例删掉，而是先抽出方法，再让案例证明方法。整体问题锚定在“大纲”或“脚本”等前部标题上，局部只标最适合补“为什么、怎么调、怎样复用”的位置；不使用文末全文评论。

### 5. 检查内容结构与节奏

- 开头优先交代系列位置、本期玩法、适用人群或最终产物，不需要用几百字铺痛点。
- 痛点只保留能自然引出本期 Skill 的部分；系列稿不必每期重新从零讲背景。
- 每个主讲 Skill 的引入、操作、结果应互相对应，不在结果段突然出现新能力。
- 重复讲同一个跨端、同一个效果或同一组步骤时合并，避免挤占真正的教学判断。
- 结尾完成本期任务或自然引出下一期，不强制统一 CTA。

### 6. 检查每个 Skill 的认知顺序

- 每个主讲 Skill 先用作者自己的话讲清功能、适用场景和主要产物，再让当前案例演示怎么使用以及效果如何。痛点钩子可以在前，但观众不能只看见一个行业案例，直到最后仍不知道这个 Skill 的通用能力。
- 跨场景例子用于帮助观众迁移。例如介绍浏览器 Skill 时，可以用自媒体信息搜集、校园通知整理、招聘岗位筛选等短例子说明它会自动打开、搜索、抓取、过滤和整理；不要求把所有例子逐个演示。
- 产物不能只写“生成内容”。应按对应 Skill 讲清实际会得到什么，例如标题、口播、镜头、字幕、转化引导或结构化报告，并把产物和省时、降门槛、稳定性中的真实价值连起来。

### 7. 检查用户视角与人话

好的教程能听出作者在回答：我遇到了什么、我为什么选它、我怎么判断结果、我会怎样继续改。不能像在念产品手册，也不能让专业术语和长 Prompt 形成“劝退感”。

批注先说明观众会卡在哪里，再给最小修改动作。不要把内部术语“能力闭环、教程深度不足、证据不完整”原样丢给达人。

### 8. 处理成立但拖节奏的内容

- 内容事实成立，不代表一定适合保留原长度和位置。若前一段已经完成总结，后一段只是换句话再次收束，应明确建议压缩或合并。
- 这类意见只有在重复或过长已经明显挤占教程、削弱节奏时才落批注；普通的句子润色仍属于可选优化。
- 评论可以写成“内容没问题，但这段和上面重复了，压成一句或并到结尾即可”，让达人知道保留什么、删什么，而不是只写“节奏不好”。

## Skill 产品资料怎么用

产品资料分三级：

1. 当前官方 Skill 的 `SKILL.md`、实时产品资料：核对功能、输入、输出和硬边界的首要依据。
2. `doubao-skill-handbook.md`：覆盖 108 个内置 Skill，用于发现适用场景、输入输出、可延展能力和易混点。
3. 模型常识：只能帮助理解，不可单独判定产品错误。

手册适合回答“达人是不是只讲了很窄的一角”“还有哪些真正有用的使用思路可以作为教程素材”。如果手册与官方 Skill 冲突，以官方 Skill 为准；只有手册、没有官方佐证时，最多记为内部待核实或可优化，不能生成 `feature_error` 批注。

## 真人样本的使用边界

- 检索相似案例时优先看“历史原稿—真人意见—修改后内容”三联，而不是孤立复制评论。
- 同一案例的具体 Skill、行业、话术顺序不是通用规则；只学习它为什么妨碍理解、如何用更低成本修正。
- 真实评论也可能过严、过时或只适用于当期方向。与现行 Brief、会议、记忆碎片冲突时，历史评论让位。
- 解决状态不代表意见必然正确；修改后文本只是结果证据，不是标准答案。
