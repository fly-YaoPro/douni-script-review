# HTML 玩法验证 Demo

本文件用于把一至两个核心玩法假设做成浏览器可直接运行的真实游戏原型。Demo 是独立交付路径：GDD 定义玩法，前端或开发能力实现，浏览器能力完成真实运行检查。

## 目录

1. 选择验证问题
2. 定义可玩切片
3. 组织实现
4. 反馈与表现
5. 调参与观察
6. 运行验证
7. 交付

## 1. 选择验证问题

先写一句可被游玩结果推翻的假设：

> 当玩家需要在蓄力伤害与暴露时间之间取舍时，会根据敌人预告主动中断蓄力，而不是始终把蓄力拉满。

同时定义：

- 玩家要完成的任务；
- 能支持或反驳假设的可观察行为；
- 一个护栏信号，避免用更差的整体体验换目标行为；
- 本 Demo 不负责证明的内容。

把“实现运行”和“玩法成立”分开判断；验证过程依赖真实操作和系统反馈。

## 2. 定义可玩切片

切片必须形成：

`进入 → 读取局面 → 操作与选择 → 即时反馈 → 状态变化 → 成功或失败 → 局后反馈 → 重开`

只保留验证所需的 P0：

- 一个清楚目标或持续压力；
- 至少一个具有代价的玩家选择；
- 能让玩家理解原因与结果的反馈；
- 胜负或明确的阶段结束；
- 无需刷新页面即可重新开始。

敌人、关卡、成长和内容数量以反复暴露目标选择为准。视觉可以占位，信息反馈和操作手感保持完整。

## 3. 组织实现

联合可用的前端或开发能力实际创建项目，不只输出代码片段。根据规模优先选择最小可靠技术：

- 单屏、2D、短循环：HTML Canvas 或轻量 DOM/CSS/JavaScript。
- 多面板调参：游戏画面与独立调试面板分层，避免调试 UI 挡住操作。
- 需要复杂资产、物理或多人网络时先收缩验证问题；HTML Demo 不扩张为生产工程。

实现时：

- 将规则状态、渲染、输入和参数分离，避免所有逻辑塞进单个事件回调；
- 为当前规则集设置唯一 `ruleset_id`，让策划参数表、Demo、调试面板和测试读取同一配置对象；禁止复制数值后分别维护；
- 为移动、冷却、生成和动画使用一致时间基准，切换标签页后不产生巨量补帧；
- 对键盘、指针和触控输入明确按下、持续、释放和取消语义；
- 处理失焦、页面缩放、不同像素密度和窗口尺寸变化；
- 提供固定随机种子或可重复场景，只在随机性本身是验证对象时开放随机。

登录、商城、背包、剧情页和复杂菜单只在它们直接参与验证假设时进入切片。

## 4. 反馈与表现

反馈围绕玩家读懂局面和结果：

- 危险在生效前有可学习预告；
- 输入后立即出现动作确认；
- 命中、受击、格挡、失败和状态切换在形状、运动、色彩或声音上可区分；
- 关键数值与状态靠近决策位置，不让玩家在远处面板来回找信息；
- 镜头、震动、粒子和音效有强度层级，不同时抢占注意力；
- 控制说明短小，开始游玩后不持续遮挡。

视觉风格保持统一，游戏界面围绕目标机制设计；敌我、危险区、目标和可交互物始终清晰可辨。

## 5. 调参与观察

关键杠杆集中配置，并写明单位、初值、合法范围和重置方式。根据验证需要加入：

- 可折叠参数面板；
- 暂停、慢放、单步或重置；
- 碰撞区、状态、冷却与事件日志显示；
- 局后摘要：选择次数、成功率、承伤、耗时、资源变化或关键事件序列；
- 导出或复制本局数据的轻量入口。

只记录能回答验证问题的事件。事件名称、触发时点和分母必须明确，避免收集大量无法解释的日志。

把共享配置源、`ruleset_id` 和运行路径写入设计契约。文档中的参数表从同一配置生成或逐项回读核对；原型中不另设隐藏的初始资源、敌人奖励、解锁时间或胜负阈值。

## 6. 运行验证

交付前先在设计契约的 `prototype.journeys` 中定义标准路径、失败恢复路径和题目暴露的高风险路径，再在真实浏览器中逐步执行，至少检查：

1. 首次加载无阻断错误，资源路径正确。
2. 键鼠或触控输入与说明一致，失焦后不会卡键。
3. 核心规则、碰撞、冷却、计分和状态恢复符合规格。
4. 成功或阶段结果、失败、局后反馈和重开都能重复执行；没有静默软锁。
5. 常见桌面和目标移动尺寸下画面不裁切，控制仍可用。
6. 连续重开、极端输入、无目标、资源耗尽和窗口切换不破坏状态。
7. 参数调节和日志确实影响并记录目标机制，且与文档中的同名参数一致。
8. 教学浮层、隐藏面板和装饰层不会拦截当前应允许的输入；强制教学只阻止规格明确禁止的操作。
9. 关卡、路线、单位和解锁状态与文档一致；成功态、失败态和恢复态都能实际到达。
10. Canvas/WebGL 首帧像素非空，关键对象位于可见区域；常见桌面和目标移动视口中没有文字、按钮或画面相互遮挡。

每条路径只有真实执行后才写 `passed`，并记录运行方式、视口、关键结果和必要截图或日志。只阅读源码、只确认页面打开、只检查 DOM 存在或由实现者口头确认，都不能标记通过。

发现错误直接修复并重新运行受影响路径及一条正常回归路径。所有必需检查通过后，将 Demo 标记为“原型验收通过，可用于验证”；玩法结论由后续真实玩家证据支持。浏览器或自动化能力不可用时明确标记 `not_run`，交付源码但不得声称原型已经验收。

## 7. 交付

至少提供：

- 可直接访问的运行入口，或完整源码与最短运行说明；
- 一屏内可读的操作说明；
- 要验证的假设、建议任务和观察信号；
- 关键参数及其默认值；
- 本切片明确不覆盖的范围。

用户需要正式方案时，把假设、规则、参数和验证说明放入飞书云文档，链接真实可玩入口，并附上与验收版本一致的单文件 HTML 或源码 ZIP。运行入口用于试玩，附件用于留档、复现和交接。
