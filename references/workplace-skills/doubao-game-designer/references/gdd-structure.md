# 成熟 GDD 的写法

完整 GDD 本身建立一个项目的当前设计真值。模板只是最终信息架构，不是推理顺序或质量证明；先在内部闭合玩家局面、核心选择、循环、最小范围、关键规则和验证，再直接从设计首页进入游戏，不在 GDD 前另写项目定义或方向比较。用户有明确约束时继承，范围内缺失项由策划完成；项目事实、统计口径、实现状态和真实产能的证据缺口留在内部基线，正式方案使用有明确来源属性的设计初值、合法范围与校准规则；只有高影响分叉无法安全代定且会让任何方案失真时才在成稿前请求裁决。

## 1. 先建立入口

完整 GDD 先做一张可独立阅读的“设计首页”。它不是摘要目录，而是团队理解和裁决设计的共同入口。

首页按信息密度组织：

| 区域 | 内容 |
|---|---|
| 项目一句话 | 玩家身份 + 核心动作 + 目标 + 主要阻力 |
| 游玩条件 | 玩家、平台、输入、单局时长、单人/多人 |
| 玩家承诺 | 最有辨识度的能动性与代价 |
| 支柱 | 2–4 条裁决规则，各带一个反例 |
| 核心动词 | 实际输入或高频认知动作 |
| 循环一句话 | 行动如何改变状态并引出下一次选择 |
| 范围 | 当前要证明什么、明确不做什么 |
| 关键结论 | 本稿已经裁决、需要团队执行的设计决定 |
| 主要读者 | 谁将据此实现、评审或做决定；内部短稿可省略 |

支柱必须能拒绝功能。“高自由度”“沉浸世界”“丰富策略”不能单独充当支柱。有效写法例如：

> **危险必须先可读。** 高收益行动可以严厉惩罚失误，但攻击前必须暴露一种可学习信号。无预告的随机秒杀不进入范围。

## 2. 用玩法走读校准抽象设计

设计首页之后，立即写一个 60–120 秒的连续游玩片段。选择最能展示游戏差异的正常场景，不选宣传片式高光。

走读至少覆盖：

1. 玩家进入时已有的目标和资源。
2. 第一眼能读到的信息。
3. 一次核心输入与即时反馈。
4. 一次需要比较的选择。
5. 选择的机会成本、风险或不可逆后果。
6. 系统如何改变下一步局面。
7. 一次小成功、失败或恢复。

不解释“这里体现了策略性”。让动作和后果自己证明。

差的写法：

> 玩家通过灵活操作和资源管理击败敌人，获得丰富奖励，并进入下一阶段。

可用的写法：

> 左侧声呐亮起两只小型清道蟹，右侧则是一团会持续泄漏氧气的渔网。玩家只剩 28 点氧气。先清怪能拿到升级经验，但渔网再漏 8 秒就会污染整片区域。玩家用推进器穿过蟹群，吃下一次擦伤，先割断渔网；污染条停止上升，推进器也因过热锁住 3 秒。蟹群围上来，刚才省下的修复泡沫此时变成唯一脱身手段。

不要复用示例中的题材和名词；学习其“局面—选择—代价—反馈—新局面”结构。

## 3. 组织玩法架构

### 三层循环

| 层级 | 关注问题 |
|---|---|
| 瞬时 | 玩家持续输入什么；如何读局面；一次动作怎样反馈 |
| 单局 | 如何准备、承压、选择、成长、胜负、结算和重试 |
| 长期 | 为什么开启下一局；跨局变化带来什么新选择 |

不是所有游戏都需要长期留存层。解谜短篇、一次性叙事或艺术游戏可以用“章节推进/认知积累”描述，或明确没有跨局系统。不要自动填每日奖励、赛季和社交。

三层之间写明传递物：资源、能力、信息、地图变化、关系状态或玩家知识。只写时间尺度而没有传递关系，仍不算架构闭合。

每层循环都检查完整因果：

`信息/压力 → 玩家行动 → 状态变化 → 可感知反馈 → 玩家理解 → 新机会/压力 → 下一次行动或退出`

若只能解释“玩家拿到奖励所以再玩”，还没有说明玩法本身为什么成立。

### Game Flow

使用 SVG 流程图表达从启动到下一局的主要状态，覆盖局前准备、单局、结算、成长与返回路径。补充退出、失败、断点恢复和真实分支，不把页面清单当作流程。

## 4. 拆分模块规格

GDD 正文保留模块摘要、与核心循环的关系和关键规则；达到下列任一条件时拆成独立规格：

- 单个模块超过两屏且多人需要频繁查阅。
- 参数、状态或边界会独立迭代。
- 程序、关卡、UI 或测试需要不同视图。
- 模块有独立负责人、版本或准出条件。

每份模块规格开头写清：

- 适用版本与状态：当前定义 / 已实现 / 已废弃。
- 目的与负责的玩家体验。
- 依赖和被依赖模块。
- 本轮变化与已经裁决的取舍。

正文只保留当前真值。讨论过程、旧规则和被否决方案进入决策记录，不和现行规则混排。

## 5. 建立章节依赖

长文不是十九个并列章节。先建立依赖：

`设计承诺 → 玩法走读 → 循环 → 核心机制 → 内容/UI/反馈 → 首个切片与验证`

面向立项、发行或制作准备时再延伸：

`玩家/市场依据 → 产品定位 → 设计承诺 → 技术与内容要求 → 制作范围 → 里程碑门禁 → 商业结果与风险`

下游章节不能擅自改变上游规则。可用紧凑追踪表记录：

| 上游决定 | 下游影响 | 验证/门禁 | 变化时需更新 |
|---|---|---|---|

正式交付前必须做一次跨章节一致性检查：抽取首页、玩法走读、循环、状态表、配置表、路线/内容表、示例、日志字段和测试用例中的关键对象、数字、术语、事件顺序和胜负条件，逐项与权威规则真值核对。发现不一致时先改权威规则，再同步引用处；不能让不同章节各自保留一套“适用情境”而不说明版本或切片。

对外文档可以把实现细节移到附录，但不能删除证明游戏成立的玩法走读、核心循环和首个切片。

## 6. 随项目阶段控制深度

| 阶段 | 优先写 | 不属于本阶段 |
|---|---|---|
| 概念 | 首页、玩法走读、核心循环、最大风险 | 大量内容、长期经济、生产排期 |
| 原型准备 | 输入、规则、反馈、参数范围、最小切片 | 正式资产、完整运营 |
| 立项/Greenlight | 决策摘要、核心设计、证据、切片、范围、门禁、风险 | 未经来源支持的市场与收入承诺 |
| 制作准备 | 模块规格、依赖、内容结构、验收 | 没有专业评估的工期承诺 |
| 制作迭代 | 当前真值、变更影响、回归范围 | 重复讲项目背景 |
| 运营 | 数据口径、经济影响、活动规则、回退 | 没有基线的提升承诺 |

即使项目仍在早期，也交付该阶段完整的当前设计；“完整”指当前阶段需要的决定闭合，不虚构不属于该阶段的章节。所有设计分叉在成稿中裁决，只有冲突的用户硬约束使任何方案失真时才在成稿前请求裁决。

## 7. 维护当前真值

变更记录写变化，不重写整份摘要：

| 字段 | 内容 |
|---|---|
| 日期/版本 | 何时生效 |
| 变化 | 哪条规则、参数或范围改变 |
| 原因 | 新证据、制作约束或设计取舍 |
| 影响 | 哪些模块和内容需要同步 |
| 状态 | 当前生效 / 已实现 / 已回滚 |

文档标题短而准确；层级可导航；核心规则能通过搜索找到；表格和图只在比文字更快时使用。成熟不等于更长，而是读者能更快找到当前问题的答案。
