# 游戏设计工作流

## 核心任务

把用户的创意、现有方案、配置和试玩证据转化为一个确定、可制作、可验证的当前项目。先让玩法成立，再展开文档；章节组织信息，不替项目补系统。

所有判断沿用同一优先级：

`用户硬约束与当前阶段 > 有来源的项目事实和配置 > 已确认且仍生效的历史决定 > 设计初值与工作假设 > 模板完整度和扩展创意`

## 设计脉络

`读题 → 立界与范围冻结 → 诊断 → 求解 → 机械保障 → 复算 → 闭合 → 生产检查 → 成稿反审 → 交付`

以上顺序表达设计依赖。任务可以合并或省略不相关环节，过程沟通只呈现会影响用户决定或交付的状态。

### 读题

完整读取提示词、附件、链接、旧稿、配置与多轮记录，先看三件事：

- 用户要解决什么问题；
- 当前处于概念、方案、规格、制作还是迭代阶段；
- 交付物是 GDD、玩法方案、单项规格、评审、修订还是可玩 Demo。

交付物决定覆盖面，不决定设计权限。完整 GDD 可以带严格边界，局部方案也可以拥有较大的设计空间。

### 立界

先建立一页内部项目基线：

| 基线 | 处理 |
|---|---|
| 结构不变量 | 原样继承对象、数量、归属、顺序、阶段和公式，如“30 张卡池中构筑固定 12 张牌组” |
| 核心选择 | 标出承载玩家幻想的最小决策，范围收缩时优先保护 |
| 硬约束、冻结项与已确认决定 | 作为本轮权限边界 |
| 有来源的当前事实 | 保留版本、场景、样本与统计口径 |
| 允许改动面 | 与现有对象组成本轮设计材料 |
| 设计初值 | 给出值、单位、合法范围与调整信号 |
| 容量 | 记录人员、人日、预算、截止时间与阶段 |

示例、测试、账本和 Demo 都使用同一组结构不变量；改写后的句子若改变了原始对象关系，先修正理解再设计。设计值与当前事实分开，外部输入回指真实文件或 URL，草稿和计算结果不反向成为现网证据。

#### 决策权限

平台输入、目标玩家、玩家关系、联网方式、核心循环、商业形态和制作规模共同定义产品身份。材料只给出模糊类型或创意，且其中的缺失会让玩法、交互或生产形态产生两个以上合理方向时，在正式设计前集中追问一轮 1–3 个最关键问题；每题给出推荐默认及不同答案会改变什么，用户可以直接授权“你来定”。材料已有答案、用户已授权代定或存在明显更优默认时，直接裁决。

局部规则、反馈、异常处理、内容量和测试参数由策划完成。用户设置阶段门禁时停在该阶段；没有阶段门禁时直接完成所需产物。

#### 范围锁

用户给出允许改动面、冻结项、现有配置或固定容量时，以“现有对象 × 允许杠杆”组成本轮设计材料。方案从这组材料出发；新增责任只有在它是核心证明不可替代的一环、拥有授权且容量中有明确交换项时进入 P0。

允许字段能直接决定的结果写成确定规则；只能改变发生概率的结果写清影响路径与趋势指标。目标强于允许面时，交付当前权限能够成立的结果与客观验收，不用相邻系统补齐目标。

命中范围锁时，在进入诊断与求解前读取 [preflight-contract.md](preflight-contract.md)，只录入原始材料、允许面与冻结项并执行 `--freeze-scope`；方案形成后再补其余风险字段。

### 诊断

把任务压成一句可观察的问题：

> 在什么局面，哪类玩家因为哪条规则采取了什么行为，结果为什么偏离目标？

建立最短因果链：

`局面 → 可见信息 → 可选动作 → 代价 → 规则结算 → 反馈 → 下一次选择`

优先处理没有选择、代价不可读、结果无法归因和失败后无法继续。试玩意见先回到目标、奖励、空间、敌人、状态、参数、教学与反馈寻找最高影响原因；定性反馈保持定性，根因证据不足时形成可验证假设。

再写一句本轮的胜负判断：在什么场景下，哪项证据达到什么条件才足以证明方案成立。后续计算、测试和 Demo 围绕这句话组织。

### 求解

方案沿同一条求解链形成：

`玩家问题 → 允许杠杆 → 现有对象的变化 → 规则结算 → 玩家结果`

先盘点现有运行能力，每项候选机制都回到项目基线中的对象与杠杆。无法映射的内容属于范围扩张；需要新的行为、状态、目标逻辑、表现、界面、数据或跨专业接线时，按新增责任计入范围和容量，并同时写明解决的问题、授权依据和被替代、删除或延期的内容。

简化围绕核心选择减负：先压缩内容量、操作频率、表现和生产责任，再考虑替换承载核心乐趣的决策。一个更省事但让核心选择失去精度或代价的方案，不算同一玩法的轻量化。

关键关系通过规则成立：

- **定位**：同一对象在某类局面更有效，也在另一类局面明显低效。
- **克制**：正确选择改变时间、空间、目标或资源关系，错误选择承担可观察代价。
- **协同**：A 改变 B 的规则或适用窗口，而不只是两个加成相加。
- **构筑**：有限选择形成互斥、机会成本或先后依赖。

每个关键关系给出一个正例和反例，并在同一基线上复算。移除名称和说明后结果没有差异的关系继续回到机制层。

用一段 60–120 秒的连续游玩检查方案：玩家看见什么、比较什么、执行什么、系统怎样结算、局面如何变化，以及失败后如何恢复。真实走读优先于抽象形容词。

### 机械保障

机械工具验证设计，不替代设计。当错误能够被结构化校验可靠发现，并且会显著影响范围、数值、规则或交付时，建立最小设计契约。常见信号包括：

- 有明确的允许改动面、冻结项、当前配置、阶段或容量；
- 涉及公式、概率、资源、升级可达性、时间轴或相互依赖的账本；
- 涉及持续状态、重复触发、同帧并发、胜负、存档或恢复；
- 根据试玩证据承接多轮修订；
- 交付研发、QA、正式配置或 HTML Demo。

建立契约时读取 [preflight-contract.md](preflight-contract.md)，只开启当前风险对应的字段；任务涉及复杂状态、经济循环、滥用风险、试玩承接或研发交接时，再读取 [design-integrity-and-handoff.md](design-integrity-and-handoff.md)。

```bash
# 未在立界阶段初始化契约时执行
python scripts/validate_design_contract.py --init design-contract.json
# 选定方案并完成计算后执行
python scripts/validate_design_contract.py design-contract.json
```

早期创意讨论与方向比较使用项目基线和设计判断即可。契约是反证风险的测试夹具，不是第二份 GDD；空字段不为通过校验而补写。

### 复算

累计经验、概率、DPS、EHP、TTK、价格、资源、时间与人日读取 [numerical-validation.md](numerical-validation.md)。第一份数值产物来自计算工具或脚本：

`输入来源 → 公式 → 单位与取整 → 正常值 → 边界值 → 设计结论`

先把本轮必须证明的数值问题写成可证伪命题，明确比较对象、场景或时间窗、决定性指标和通过条件，再映射到断言；用户给出的公式属于上游约束，改变公式是一项设计改动。关键数值至少覆盖正常与边界场景；存在递归、叠加、刷取或支配策略时增加滥用场景。若关联断言失败仍不改变设计结论，它只是辅助指标，继续寻找真正承担结论的证据。

推导沿真实玩家路径展开。阶段成长从资源或时间开始，经过机会次数、掉落或奖励、重复与槽位覆盖，最后到达玩家状态；同时检查终点是否达标和中间阶段是否有可感知变化。倍率、百分比提升和百分点使用各自口径，例如 `4.31 倍 = 提升 331%`。

缺少现网基值时，可以对同一对象、同一字段使用 `现状 = 1.00` 的相对表达，并标为设计初值；不同对象、时段或口径之间的关系仍需要各自来源。

成稿后从正文重新提取联合效应、阶段序列、总量和回滚阈值，一次复算并同步表格、示例、配置、测试和 Demo。缺少产出时点、攻击频率或其他决定性输入时给出可证明区间与校准条件，不把单一猜测写成必然结论。每个派生量同时满足：

`算术正确 → 变化方向对应问题 → 结果满足正文阈值`

计算证明数学成立；平衡、趣味和玩家行为由对应试玩证据支持。

### 闭合

持续、累积、可重复、可消费或跨场景的规则写成：

`创建事件 → 生效条件 → 重复策略 → 消费或退出 → 结束状态 → 打断、死亡、切场景与读档恢复`

同一事件使用唯一身份，跨帧检测保持一次结算。并发先定结算阶段，再定阶段内优先级；展示顺序沿用真实结算顺序。终局确定后，已经失去玩家意义的选择、奖励或操作按权威规则消费、结转或取消。

复杂规则使用状态图或转移表；正文、配置、示例、测试和 Demo 引用同一当前定义。

### 生产检查

从当前改动触及的责任面选择风险：

| 责任面 | 核心证据 |
|---|---|
| 运行与性能 | 峰值规模、热点、预算与降级策略 |
| 状态与数据 | 写入来源、恢复、迁移、版本与回滚 |
| 联机与并发 | 权威端、事件身份、顺序、幂等与恢复 |
| 内容生产 | 配置和资产数量、复用面、单位成本与产能 |
| UI 与输入 | 完整玩家路径、目标设备与异常输入 |
| 集成与 QA | 接线、数据验证、回归、负责人和回退点 |

逐项沿 P0 改动追踪第一个非玩法后果：规模或频率变化落到性能，分层、奖励或实验变化落到数据与商业口径，新内容落到生产管线，新状态落到持久化与集成。只写会改变上线判断、容量或回退动作的风险。

完整方法见 [business-and-production.md](business-and-production.md)。容量先保留接线、数据验证、QA 与修复，再分配功能、配置、内容和表现；P0 总量保持在可用容量内。新埋点、日志、看板或发布能力作为独立生产责任判断。

### 成稿

产物结构服从用户目标：

| 目标 | 正文 |
|---|---|
| 完整 GDD | 当前项目的完整设计 |
| 游戏、活动或版本玩法方案 | 支撑评审与选择的可执行方案 |
| 战斗、成长、经济、关卡、引导或数值 | 继承必要上游的单项规格 |
| 评审、点评 | 保留原文，按影响分级给出证据和最小修改 |
| 修订、直接改 | 更新真实影响面，保留未受影响内容 |
| 可玩 Demo | 原型、验证假设、运行证据与结论 |

#### 完整 GDD 主干

用户未指定模板时按以下信息顺序组织，章节随项目责任伸缩：

1. **设计首页**：定位、目标玩家、平台输入、玩家关系、单局时长、核心幻想、设计支柱、核心动词、循环、范围与非目标。
2. **具体玩法走读**：连续游玩中的信息、选择、代价、结算、反馈与恢复。
3. **玩法架构**：瞬时、单局与必要的长期循环；资源、能力、信息和目标如何传递；Game Flow SVG。
4. **核心机制**：目的、输入、权威规则、生命周期、反馈、数值、边界、依赖与验收。
5. **条件模块**：只展开会改变玩家决策、实现责任或验收结果的系统。
6. **首个可玩范围**：P0、P1、非目标、验证假设、阈值、责任、容量与回退。

完整 GDD 读取 [gdd-structure.md](gdd-structure.md)、[play-and-loop-principles.md](play-and-loop-principles.md) 与 [writing-style.md](writing-style.md)。

单项玩法与系统读取 [mechanics-and-systems.md](mechanics-and-systems.md)；关卡、内容和引导读取 [content-and-onboarding.md](content-and-onboarding.md)；评审与多轮修订读取 [review-and-revision.md](review-and-revision.md)。

完整度来自受影响系统的因果、生命周期和交接闭合，不来自系统数量。成稿只展开已经裁决的方案，不在章节中生成新的机制；用户要求候选比较时可以保留分叉，进入正式 GDD 后完成裁决。内部约束账本、候选比较、工具过程和校验日志不进入正文。

### 成稿反审与交付

停止写作，先把成稿中的对象、数量、归属、顺序、阶段和公式与项目基线逐项对齐；任一结构不变量发生漂移，先修正再进入长评审。随后读取 [adversarial-review.md](adversarial-review.md)，从原始需求重新检查：

- 用户约束、当前事实和阶段是否完整继承；
- 每项实质改动是否拥有设计权限；
- 关键关系是否在正反场景中成立；
- 数字、生命周期、容量和生产责任是否闭合；
- 正文、配置、示例、测试和 Demo 是否使用同一规则。

审查与写作分离。范围受限时，审查者先从完整正文重新抽取改变规则、对象、状态、界面、数据或生产责任的实质改动，不沿用作者的改动清单；逐项回指项目基线中的允许面与冻结项。使用统一契约时再对照 `proposed_changes → authority → 冻结字段`。无法映射、映射粒度更宽或只靠正文自我授权的内容视为范围越界，退回作者用已授权的最小杠杆解决。

随后从原始需求重建必须证明的数值问题，不沿用作者“已经算过”的结论；逐项检查公式来源、可达性、通过条件、跨产物一致性和最强可钻路径。发现问题后不扩写评审报告，由作者按以下权威顺序修订当前方案：

`用户与项目事实 → 公式 → 设计参数 → 派生结果 → 示例与测试 → Demo → 叙述`

上游正确时修改下游；设计关系不成立时只调整拥有权限的最小杠杆。同步受影响产物后重新运行本轮实际使用的计算、测试和独立反审，阻塞项清零才进入交付。

启用范围锁时，对完整本地正文追加：

```bash
python scripts/validate_design_contract.py design-contract.json --draft <正文路径>
```

修复全部阻塞项后读取 [lark-document-delivery.md](lark-document-delivery.md)。交付载体在读题时确定；未见明确的对话交付指令时就是飞书云文档。先完成全部正文、图文分工与全文回读，再一次性创建或更新文档；写入只承担落版，随后回读验收。最终回复前确认真实文档链接已经存在。完整 GDD 的 Game Flow 使用非空 SVG 画板，其他状态、资源流和关键界面只在图示能降低判断成本时增加。

## HTML 玩法验证 Demo

用户明确要求可玩 Demo，或核心风险只能通过操作判断时读取 [html-gameplay-demo.md](html-gameplay-demo.md)，联合前端、开发、浏览器和托管能力完成真实原型。

- 用一句可证伪假设定义玩家任务、目标行为和护栏信号。
- 切片闭合进入、读取、操作、反馈、状态变化、结果、局后反馈与重开。
- 规则说明、配置、调试面板、统计与测试共享 `ruleset_id` 和配置源。
- 在真实浏览器走通标准、失败、恢复和题目暴露的高风险路径。

正式方案与 Demo 同时交付时，飞书文档链接真实运行入口，并附同一验收版本的 HTML 或源码 ZIP。可下载文件是交付件，在线预览是运行证据，二者使用同一 `ruleset_id`。

## 交付前回看

以下内容是质量信号，不是正文目录或内部检查报告：

1. 当前方案逐条继承用户约束、事实、阶段和已验证改动。
2. 核心选择在真实走读和正反场景中成立。
3. 持续规则生命周期闭合，并发和恢复具有唯一结果。
4. 数字由工具复算，输入、公式、单位、取整、边界和下游引用一致。
5. P0 只保留核心责任，容量包含集成、验证、QA 与修复。
6. 生产风险对应真实改动面，玩家从入口到结果、失败恢复和重试可达。
7. 正文、配置、示例、测试、图示和 Demo 使用同一套当前规则。
8. 就绪等级与已有证据一致；原型结论来自运行，体验结论来自真人试玩。

用户要求成稿时直接交付真实产物。正式文档语言具体自然，不保留未知、待核实、后续或占位章节。
