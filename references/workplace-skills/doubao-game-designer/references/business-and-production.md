## 1. 先确定读者和决定

商业/制作附录不是“显得专业”的章节集合。先回答：

- 谁会读：设计团队、制作人、管理层、发行商、投资人、平台方还是合作工作室。
- 要促成什么决定：继续原型、进入垂直切片、签约、给预算、确定商业模式、锁平台或批准制作。
- 项目处于概念、原型、制作准备、制作、测试还是运营阶段。
- 每一项外部陈述使用什么来源；无法证实且不影响设计的内容不进入成稿。

同一份材料不必同时服务全部读者。对外材料强调判断和可信度；内部规格强调当前真值、依赖和验收。

## 2. 选择交付剖面

| 交付 | 必要内容 | 条件内容 |
|---|---|---|
| 内部设计 GDD | 设计首页、玩法走读、循环、机制、内容、切片 | 商业和市场通常不展开 |
| Greenlight/立项包 | 决策摘要、设计核心、切片、团队约束、里程碑门禁、风险 | 市场和商业模式摘要 |
| 发行/投资材料 | 执行摘要、受众与定位、差异、产品模式、制作可信度、资金用途对应的范围 | 详细机制放附录 |
| 制作准备 GDD | 当前设计、技术要求、内容规模、依赖、验收、风险与处理规则 | 市场只保留影响设计的结论 |
| F2P/持续运营设计 | 核心玩法、产品经济、付费价值交换、内容与活动供给、数据口径、回退 | 当前政策与合规研究 |

不要把一页 pitch、完整 GDD、TDD、商业计划和项目排期硬塞成一个文件。它们共享真值，但回答不同问题。

## 3. 写决策摘要

让读者只看一页也能回答：

| 字段 | 内容 |
|---|---|
| 请求的决定 | 本轮希望批准、否决或补证什么 |
| 产品一句话 | 玩家、核心行动、差异和主要阻力 |
| 目标玩家与场景 | 谁在什么平台、时间和社交情境下玩 |
| 当前证据 | 已完成的原型、试玩、调研或历史数据 |
| 首要项目风险 | 哪个风险会推翻项目、触发信号和处理规则 |
| 当前范围 | 本阶段真实要做什么 |
| 团队与约束 | 已知能力、平台、预算级别或外部依赖 |
| 当前准入标准 | 满足哪些证据才允许扩大投入 |

不要用“市场巨大”“潜力无限”“玩法独特”填摘要。没有来源的市场判断不进入成稿。

## 4. 市场与竞品

只分析会改变产品或制作决定的竞品：

- **直接竞品**：相似玩法、平台、受众和购买理由。
- **间接竞品**：争夺相同时间、社交场景或消费预算。
- **标杆作品**：提供质量或制作参照，不代表直接竞争。

每个竞品回答：

1. 玩家为什么选择它。
2. 哪个机制、内容结构或商业模式真正有效。
3. 它的限制是否有可靠玩家、产品或市场证据。
4. 本项目学习、修改或拒绝什么。
5. 对方在哪些方面明显更强。

对比矩阵只列影响购买和留存判断的维度。不要用勾叉数量伪造优势，也不要把尚未实现的规划写成已具备能力。

市场定位写成有来源、可检验的产品判断：

> 对于【具体玩家/场景】，本作提供【核心价值】；相较【当前替代】，它通过【可体验差异】解决【有来源的问题】。判断依据为【调研/商店数据/试玩/愿望单等】，准入阈值为【具体标准】。

“市场空白”需要证据；没有强竞品也可能意味着需求不足。

## 5. 商业模式与产品经济

先区分：

- **商业模式**：玩家或合作方为什么、何时、为哪类价值付费。
- **游戏经济**：资源如何产出、存储、转化和消耗。
- **留存/内容节奏**：玩家为什么继续，不等于为什么付费。

选择 premium、DLC、订阅、F2P、广告、授权或混合模式时，说明受众、平台、内容供给、运营能力和竞争公平的适配，不按品类自动套用。

付费设计至少记录：

| 字段 | 问题 |
|---|---|
| 价值 | 玩家实际得到什么 |
| 时点与频率 | 何时出现，多久一次 |
| 非付费基线 | 不付费能否完整理解和享受核心玩法 |
| 对玩法影响 | 是否改变实力、时间、信息或社交地位 |
| 价格依据 | 当前平台、地区、竞品或研究来源 |
| 限制与保护 | 消费上限、冷静期、概率透明、未成年人和退款等要求 |
| 运营成本 | 需要的内容、客服、数据、审核和技术能力 |
| 失败/回退 | 指标或玩家信任恶化时如何停止、替换或回滚 |

用行为和需求分群，不用“鲸鱼/海豚/小鱼”等标签替代玩家。不得用羞辱、虚假稀缺、不可关闭提示、故意残留货币或竞争付费优势制造购买。

法律、平台政策和地区价格会变化。需要具体结论时检索当前官方来源；无法取得必要结论时在成稿前请求法务、发行或平台负责人裁决，不把待确认状态留在 GDD。

## 6. 制作范围与里程碑

GDD 提供制作门禁，不替制作人承诺人日和日期。用户已经给出可用人日、人数或截止时间时，将其视为当前方案的硬容量，而不是新的工期承诺：先划出接线、数据验证、QA 回归和修复空间，再逐项估算功能增量并加总；总量超出容量时收缩功能或启用回退。每个阶段写：

| 字段 | 内容 |
|---|---|
| 目标 | 这阶段必须证明什么 |
| 进入条件 | 开始前必须已有的决定、资产或技术 |
| 范围 | 必须真实完成、允许使用何种临时资产和明确不做 |
| 产物 | 可试玩版本、规格、内容样例、技术验证或数据 |
| 退出条件 | 什么证据允许进入下一阶段 |
| 关键依赖 | 团队、技术、外包、平台、许可或内容 |
| 失败处理 | 缩范围、替代方案、移出范围或终止条件 |

常见阶段名称可用原型、垂直切片、Alpha、Beta、上线，但按项目改名和删减。门禁是证据变化，不是“到了某日期”。

内容规模按生产单位表达：关卡、敌人、角色、动画、语音、任务、活动、平台和本地化语言。给数量之前说明模板、复杂度层级、复用关系和质量门槛。

没有团队结构、速度样本、外包报价和负责人确认时，不输出精确工期或预算承诺，只保留已经确定的制作范围、相对增量与依赖。若用户给出容量但缺少速度样本，使用保守区间并让区间上限不超过容量；不能把多项“各自看起来很小”的工作同时塞进 P0。

比较四种可执行范围：最小范围、目标范围、降级方案和延期项。每个新增功能必须说明它替代或挤出什么；“新增但总量不变”必须能在任务、资产、配置和 QA 责任上复核。

## 7. 技术要求

GDD 写“产品必须满足什么”，TDD 决定“怎样实现”。按需写：

- 平台、输入、分辨率、帧率、加载、内存和包体目标。
- 本地/在线人数、延迟容忍、断线、存档和跨平台行为。
- 数据、分析、远程配置、隐私、客服和运营需要。
- 可访问性、本地化、平台认证和内容审核要求。
- 关键技术原型、第三方依赖和回退方案。

设计方案同时检查对象峰值、投射物/特效数量、AI 数量、存档/日志量、网络或设备负担等实际生产风险。无法给工程结论时标为需技术验证，并提供更低成本回退，不把风险隐藏在“配置可调”中。

性能、设备、引擎、SDK、认证周期和平台规则必须由当前目标与工程/平台资料支持。不要把模板里的硬件表、tick rate 或 SDK 清单当默认答案。

## 8. 风险与处理规则

风险登记使用：

| 风险 | 依据/触发信号 | 概率 | 影响 | 预防 | 备选/回退 | 负责人角色 | 复查点 |
|---|---|---|---|---|---|---|---|

至少区分设计、内容、技术、团队/供应、市场、商业和外部政策。概率和影响可以用低/中/高，但要说明判断依据；不要为了凑表列十个通用风险。

每项风险必须同时给出当前采用的预防方案、触发阈值和触发后的处理规则。历史讨论进入决策记录，正文只保留当前真值。

## 9. 证据规则

外部可验证陈述分为：

- **用户提供**：注明来源和适用范围。
- **已检索来源**：给标题、日期、链接和访问日期；优先官方、平台、财报、商店或原始研究。
- **内部数据**：说明版本、样本、时间窗和口径。

市场规模、销量、玩家数、价格、留存、转化、ARPU/LTV、平台费用、认证周期、法规和地区政策必须遵循以上规则。无法归入以上来源的陈述不进入成稿；模型生成的数字不是研究结果。

项目内部的伤害、冷却、资源产量等写成当前设计值，同时给合法范围、调节目标和触发修改的阈值，不伪装成外部事实。

## 10. 组装文档

长文先建立依赖：

`玩家需求/市场依据 → 产品承诺 → 玩法支柱 → 核心机制 → 内容与技术要求 → 制作范围 → 里程碑门禁 → 商业结果与风险`

每个下游结论能追溯到上游依据；依据变化时指出受影响章节。

对外版本可把机制细节移入附录，但不能删掉证明游戏成立的玩法走读、核心循环和首个切片。内部版本可以压缩市场叙述，但保留会改变范围、平台、经济和内容节奏的结论。
