# 独立反向评审

完成本轮计算和可执行检查后，用本文件检查机器无法判断的策划质量。评审目标是判断当前稿能否支持下一步决策或开发，不是重新写一份更长的方案。

## 评审输入

- 用户原始需求、附件和后续限制；
- 当前版本草稿与实际交付物；
- 计算表、脚本结果，以及本轮使用过的设计契约和校验结果；
- 多轮任务中的上一版方案、试玩数据和已确认改动。

有独立审查能力时，审查者只接收以上原始材料，不接收作者预设的结论、期望答案或“重点帮我证明已经修好”等提示。没有独立能力时，停止改稿后从原始需求重新走读，不边写边给自己判通过。

审查先重建任务真正需要证明的问题，再看作者选择了哪些公式和证据。脚本 `PASS` 只说明送入脚本的内容自洽，不证明公式选对、关键指标齐全或最终产物一致。

## 第一遍：无损对齐

先做一遍短审，不进入章节细节：

1. 从原始材料重列对象、数量、归属、顺序、阶段和公式。
2. 在成稿、示例、测试和 Demo 中逐项寻找同一关系。
3. 重建承载核心乐趣的最小玩家选择，确认轻量化没有把它替换掉。
4. 重建本轮胜负判断，确认决定性证据失败时会推翻作者结论。

结构不变量漂移、核心选择被意外删除或证据与结论无关时，直接退回最小修改；不靠补章节修饰。

## 正文—范围对账

范围受限时，先只从完整正文和实际交付物重新抽取实质改动，再与项目基线中的允许面和冻结项对照；使用统一契约时一并核对作者记录。实质改动包括新增或改变规则、对象、状态、参数口径、界面、数据以及跨专业责任；章节标题和解释性文字本身不算改动。

每项记录正文位置，并按以下链路追溯：

`正文改动 → 解决的问题 → 允许面与冻结项 → 容量交换`

使用统一契约时再映射到 `proposed_change → authority → 冻结字段`。继承的现有能力回指有来源的当前事实或配置。正文改动无法完成追溯、实际含义宽于授权字段，或需要靠新写的正文反向解释授权时，判为范围越界；回到已有杠杆收缩方案，不补写权限。对账是内部审查材料，不进入正式 GDD。

同一轮从正文抽取所有会改变实现或玩家结果的规则表述，按规则、参数和状态归组；每组只保留一套当前定义，无法归组或与权威规则、配置、测试相冲突的表述退回统一。

## 七个评审维度

### 1. 需求与权限

- 当前方案是否解决用户真正提出的问题；
- 每项新增系统、对象、页面、状态和跨专业责任是否有授权；
- P1、建议项或换名内容是否仍属于用户限制的改动面；
- 高影响缺口是否被追问、收窄或显式阻塞。
- 章节完整度是否推动方案改写事实、跨越阶段或创造了用户未要求的系统。
- 限定任务是否以原有对象、状态和事件完成求解；新增责任是否真正不可替代并有容量交换项。

### 2. 核心玩法与玩家体验

- 玩家在具体局面看见什么、比较什么、承担什么代价；
- 结果是否制造下一次选择，而不是只增加步骤或奖励；
- 克制、风险和反馈是否由战斗与空间机制自然产生；
- 标签、提示、弹窗和文案是否在替代底层规则，或增加不必要记忆负担。
- 简化是否降低了内容与操作负担，同时保留承载核心幻想的选择精度、机会成本和反馈。

### 3. 规则闭合

- 状态进入、退出、最长持续、打断、清理和恢复是否唯一；
- 重复触发、A-B-A 绕过、并发、死亡、胜负和极值是否有唯一结果；
- 消费型效果是否先消费旧状态，再判断本次事件能否创建新状态；
- 存档是否先有明确写入时机和字段，再谈读档恢复；
- 测试预期是否违反正文规则。

### 4. 数值与可达性

- 用户的数值约束与当前设计目标是否都进入本轮计算问题；使用统一契约时是否映射到 `numeric_requirements`，并由相关断言而非无关算例覆盖；
- 每项决定性断言失败时是否会推翻对应结论；不会改变结论的代理指标只能作为辅助证据；
- 对每个决定性结论，找出最可能推翻它的关键假设或可达反例；结论不能成立时修正方案或收窄表述；
- 单位、时间基准、公式、取整、上下限和来源是否一致；
- 公式是否沿用用户或当前项目口径，概率、资源、人日和时间轴是否有工具输出；
- 标准、最低收益、提前消费和滥用路径是否都可达；
- 结论是否验证了真正的设计目标，如正确/错误配置差、EHP×DPS、TTK 或升级次数，而不只是局部算式；
- 算术成立后是否满足当前设计的通过条件；零回报、增长率倒挂、固定最优解或强制翻盘不能因为合计正确而通过；
- 缺少攻速、产出时点或真实配置时，结论是否被不当写成必然。
- 推导是否沿资源、机会次数、产出、重复/槽位覆盖到达最终状态；平均值是否掩盖毕业概率、最低路径或中间阶段无成长。
- 倍率、百分比提升、百分点，池、牌组、候选、选择和最终持有是否保持各自语义。

### 5. 交付物一致性

- 正文、配置、状态表、测试、日志和 Demo 是否引用同一规则集；
- `proposed_changes`、规则、参数、状态、容量任务、生产风险、测试和正文是否仍有被删除或未授权的名词与责任；
- HTML 是否真实走通标准、失败、恢复和结果路径；
- 浮层、隐藏面板、路线锁定、重开和成功态是否存在实际阻断；
- 文档声称已实现或已验证的内容是否有对应运行证据。

### 6. MVP、成本与风险

- P0 是否只保留验证核心假设所需内容；
- 工作量是否逐项加总并为接线、数据、QA 回归和修复留出独立容量；
- 新增项是否有明确挤出项、降级方案和回退条件；
- 每项实质改动是否沿玩家、数据、商业、技术、内容与运营追踪直接下游；会改变结论或上线安全的影响是否进入验证、风险或回退；
- 当前责任面是否检查运行性能、状态数据、联机并发、内容生产、UI 输入或集成 QA 中真正相关的风险；
- 调高刷新频率、同屏数量、投射物、特效或状态检查时，是否给出峰值规模、目标设备预算和降级动作；
- 团队、周期和当前技术能力是否支持方案，而不是只支持文档篇幅。

### 7. 证据与多轮承接

- 事实、设计初值、原因假设和体验结论是否分开；
- 试玩指标是否保留版本、样本、分母、场景和时间窗；
- 上一轮已验证有效的改动是否被保留；
- 新方案、删减项、验收指标和回退动作是否由新证据连接起来。

## 输出规则

只写能改变结论的发现，按影响分级：

| 级别 | 判定 |
|---|---|
| 阻塞 | 继续实现会得到错误结果，或无法证明当前范围可实现 |
| 严重 | 可以继续评审，但很可能破坏玩家行为、规则一致性或工程交付 |
| 优化 | 不阻断主闭环的表达、效率或体验改进 |

每条发现必须包含：具体位置或原文、反例或证据、玩家/实现影响、最小修改、回归面。不要只说“考虑不够全面”“建议进一步完善”。

最终给出 `通过 / 需迭代 / 阻塞`。只要存在范围越界、规则多版本、关键路径不可达、数值不可复算、P0 超容量、存档来源缺失或必需原型路径未运行，就不能判通过。

## 修复回路

评审发现进入当前方案，不作为附录留到以后：

`定位权威来源 → 修正公式或最小设计杠杆 → 重算派生结果 → 同步正文、配置、测试和 Demo → 运行受影响路径 → 再审`

修复遵循：

`用户与项目事实 → 公式 → 设计参数 → 派生结果 → 示例与测试 → Demo → 叙述`

- 算术或取整错误：保留权威输入与公式，替换全部派生值。
- 公式冲突：回到用户或当前项目口径；公式未被规定时，由策划选择最服务核心体验且有验证路径的一种。
- 路径不可达：保留硬约束，先修正派生结论或最小设计参数，不补造资源。
- 多产物不一致：选定当前规则集，重新生成受影响内容并运行真实路径。
- 数学成立但设计关系失败：只调整拥有权限的最小杠杆，重新做正常、边界与必要的滥用复算。
- 缺少真实数据：使用确定的设计初值、合法范围和校准规则；证据不足时降低就绪等级，不伪造现状。

作者修复后重新运行本轮实际使用的机械校验、受影响测试和一次独立复核。旧报告不能证明新版本通过；阻塞项不能仅写进风险章节后继续交付。
