# 飞书策划文档交付

本文件用于创建或更新 GDD、游戏或活动玩法方案、系统规格、评审报告与修订稿。游戏设计决定内容，载体决定阅读方式；制作细节以当前 `lark-doc` 与画板能力为准。

## 1. 内容地图

制作前明确：读者是谁、在什么场景阅读、看完要做出什么决定，以及哪些内容属于当前设计、外部事实或试玩结论。沿用主流程已经裁决的项目形态和范围，不因选择了文档载体增加无关章节。

正文从游戏内容开始。设计首页给出定位、玩家承诺、核心循环和当前范围；玩法走读使用连贯短段落；状态、参数、边界与验收使用表格；流程和关系交给必要图示。

在确定图文分工前先问：如果读者只看文字，哪个循环、状态、资源关系或关键界面最难准确判断？按问题选择表达：

| 设计内容 | 表达 |
|---|---|
| 核心循环、Game Flow、关卡推进 | SVG 流程图 |
| 状态切换、打断、失败、恢复、结算顺序 | 状态图或转移图 |
| 资源产出、消耗、回流与经济关系 | 资源流或关系图 |
| HUD、输入反馈、新手引导和关键界面 | 可编辑低保真界面 |
| 系统依赖、内容结构和模式关系 | 简化关系图 |
| 参数、规则、边界和验收 | 紧凑表格 |

任一项会影响实现、测试或评审时，生成一张最能暴露问题的主图；另一类信息同样会改变判断时再增加。图示应可编辑、紧邻对应正文，并替代一段难扫读的文字，不重复正文，也不把概念图包装成已实现内容。

## 2. 飞书画板

完整 GDD 的 Game Flow 使用 SVG 画板；核心循环、复杂状态、资源流或关键界面在图示能降低理解成本时一并使用：

1. 在长文写作前确定每张图的目标、类型、插入章节和必须出现的信息，并明确哪些文字将由图替代。
2. 图示统一使用 `<whiteboard type="svg">`；本规则优先于 `lark-doc` 的通用画板选型。
3. 优先在首次完整文档写入中直接嵌入非空画板；若必须先取得文档或画板标识，创建后立即写入内容。
4. 通过画板预览或导出检查中文、数值、节点、连线、方向、结算顺序和默认文档宽度下的可读性。
5. 图过长、留白失衡、连线交叉或文字难以辨认时，重新布局或拆图。
6. 回到正文删除已经由画板表达的步骤描述，再核对图示、正文、参数表和验收条件的术语、状态与异常分支。

完整 GDD 的完成条件包含一张非空 Game Flow SVG 画板，并通过预览与图文一致性检查；其他 SVG 画板沿用同一验收。SVG 画板无法生成时，先交付正文并明确可视化未完成及失败点。

## 3. 生成与验收

1. 策划文档采用“完整成稿—载体写入”两阶段，优先于通用文档的长文骨架路径。
2. 完成全部正文、图文分工与全文回读后再创建载体；启用范围锁时，先对实际正文运行 `--draft`。长文可少量分批传输，写入只承担落版。
3. 修改已有文档时先读取原文，保留未受影响章节、术语和格式，精准更新真实影响面。
4. 写入后重新读取文档；使用画板时同时完成预览或导出检查。

文档与 HTML Demo 同时交付时，在验证说明旁链接真实运行入口，并使用 `lark-doc` 的文件附件能力上传同一验收版本的源码：

- 单文件 Demo 直接附 `.html`；多文件 Demo 打包为 `.zip`，包含完整源码与最短运行说明。
- 文件名使用项目名与 Demo 标识，确保读者能辨认版本与用途。
- 附件用于留档、复现和交接，不能替代已经实际验证的运行入口。

交付前确认：

- 链接可访问，标题、章节、表格和画板均有实际内容。
- 文档中只有一套当前设计，关键数值、术语和规则前后一致。
- 图示与正文各自承担清楚职责，没有同一流程的重复长述。
- 更新任务保留未受影响内容，关键改动已经反映到循环、机制、界面、教学、日志和测试等真实影响面。
- Demo 运行入口可打开，附件可下载且与最后验收版本一致，外部来源链接仍然有效。

飞书能力不可用、权限不足或写入失败时，保留已经完成的策划正文，使用用户可访问的方式及时交付并说明具体失败点，不让载体问题阻断设计交付。
