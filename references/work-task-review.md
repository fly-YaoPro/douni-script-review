# 工作任务审稿

## 核心判断

- 选题符合达人身份、账号垂类和真实工作/学习需求；不是先想功能再硬编需求。
- 主线是一件完整任务，前因、操作、产出和结果连贯。不要堆多个互不相干的场景。
- 应真正使用豆包工作的 Agent/Skills 能力，不把普通问答包装成工作任务。
- Skills 服务于任务，不是无意义报菜名。需要讲清楚为什么用、输入了什么、产出了什么、怎么继续修改。
- 结果要有 Agent 感：网页、应用、工作流、多份关联交付物、连续执行或可继续使用的成果；具体形态取决于达人任务，不能机械要求每篇都生成网页或多份交付物。

## 结构与演示

- 开头 15–25 秒先交代真实痛点和最终结果。双端是否需要前置，以当前生效的审稿 Shard 和 Brief 为准；基础规则不永久写死临时推广重点。
- 抖音在约 25 秒内进入产品操作；小红书在约 20 秒内进入操作。不要机械按字数判错，要结合口播节奏。
- 需要让观众看懂任务怎样从输入走到结果；创建或改造 Skill 时通常应出现迭代、修改或复测，但不机械数交互轮次。
- 展示真实操作、真实输入和真实产物，避免只讲概念、只口播结果或假装用了功能。
- 文档中的操作说明、录屏安排和结果画面描述均可作为展示依据；没有内嵌最终视频时，不得自动判定“未展示”。
- 默认完整稿约 700–800 字、成片 1.5–2 分钟；明显偏离时结合内容密度判断，不机械数句子。
- 结尾 CTA 简短自然，不做虚假承诺，不用空泛口号。

## 常见需要批注的问题

- 需求不真实、达人身份不匹配、功能先行。
- 只会话问答，没有 Agent/Skills 的连续执行过程。
- 一条视频拼太多场景，主线断裂。
- 开头明显没有交代主题、结果或进入操作过慢。仅仅“还能更快”属于优化，不落批注。
- 创建或改造 Skill 却完全没有迭代/复测，或画面和口播明显对不上。
- 把制作说明、客户口径或内部工作流直接说给观众。

## 会议全文确认的允许项

- 自建 Skill 可以只从一个核心输入开始，例如输入成本后由 Skill 自行进行市场分析、核算和定价；只要脚本展示了如何创建、调试并复测，不要求达人把所有变量都手工填一遍。
- “一键复制同款工具”“效率翻倍”“单人完成以前多人协作的工作”等表达，在画面展示了对应工作流和结果时可以说。
- 当前阶段是否必须体现双端互通，由生效中的审稿记忆碎片控制；命中时不得为了减少步骤而删掉。
- 双端在脚本/分镜中有清楚的手机与电脑连续操作即可；手机可以远程控制实体电脑、继续输入 Prompt 并推进电脑端任务，不只是查看进度或结果，也不需要因此补云电脑。
- 云电脑是独立能力。只有稿件明确宣传设备关机后云端继续、本地硬件无关等能力时，才要求云电脑操作与口播对应。
- 不要凭静态脚本没有附成片就要求补录屏、截图或画面；只有稿件已有的文字、分镜和操作说明明确互相冲突时才指出。
